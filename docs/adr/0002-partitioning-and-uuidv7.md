# ADR-0002: Партиционирование по месяцам + UUIDv7 как первичный ключ

**Язык / Language:** Русский · [English](./en/0002-partitioning-and-uuidv7.md)

← [Все ADR](./README.md)

## Контекст

Требование — выдерживать 500 000 уведомлений/сутки без деградации. При строке ≈ 250 Б и
4 индексах ≈ 500 Б это ≈ 250 МБ/сутки, ≈ 90 ГБ/год (расчёт и замеры — `docs/performance.md`).
Непартиционированная таблица на сотни миллионов строк деградирует по нескольким осям сразу:

- индексы растут без возможности дёшево уменьшить объём хранимых данных (`DELETE` не
  освобождает место на диске без `VACUUM FULL`, который блокирует таблицу);
- retention («не храним уведомления старше N месяцев») превращается в массовый `DELETE`,
  создающий VACUUM-долг и долго удерживающий блокировки строк;
- если PK — `UUIDv4`, вставки случайно разбросаны по всему B-tree индекса, что портит
  локальность страниц и раздувает индекс сильнее, чем монотонный ключ.

## Решение

1. **Партиционирование по диапазону `created_at`** (`PARTITION BY RANGE`), с помесячными
   партициями и `DEFAULT`-партицией как страховкой от неожиданных дат.
2. **`id` — UUIDv7**, генерируется приложением (`uuid@11`, `v7({ msecs })`): монотонно
   возрастает во времени, что даёт такую же локальность вставки в B-tree, как автоинкремент,
   но остаётся глобально уникальным без координации между инстансами.
3. **Составной первичный ключ `(id, created_at)`**: партиционированная таблица требует, чтобы
   ключ партиционирования входил в любой уникальный/первичный индекс.
4. **`created_at` выводится из `id`, а не хранится независимо**: старшие 48 бит UUIDv7 — это
   Unix-время в миллисекундах. Публичный API остаётся «по `id`»
   (`PATCH /notifications/:id/read`), но `created_at` для `WHERE`-условия вычисляется на
   сервере из `id` без похода в БД. Это даёт **partition pruning**: `WHERE id = $1 AND
created_at = $2` не сканирует все партиции, а сразу обращается к одной.
5. **Инвариант:** `created_at` пишется как `new Date(msecs)` из тех же `msecs`, из которых
   собран `id`, с точностью до миллисекунды (без микросекунд). Нарушение инварианта делает
   равенство `created_at`, вычисленного из `id`, неверным, и запросы «по id» перестают находить
   строку. `msecs` берётся из `clock_timestamp()` самой БД, а не из процесса Node.js — это
   устраняет расхождение часов между инстансами приложения.

## Альтернативы

- **`UUIDv4` как PK** — случайные вставки в B-tree ломают локальность страниц и разбухают
  индексы на больших объёмах. Отклонено.
- **`BIGSERIAL`** — монотонен и локален так же хорошо, как UUIDv7, но требует координации
  через последовательность БД (единая точка синхронизации при горизонтальном масштабировании
  вставок) и утекает во внешний API информацию о количестве и порядке созданных записей.
- **Партиционирование по неделям вместо месяцев** — при текущем объёме (≈7.5 ГБ/мес) месячные
  партиции дают удобный баланс между числом партиций и их размером. Пересмотреть при кратном
  росте нагрузки (см. триггер ниже и `docs/performance.md`).
- **Отдельная колонка `created_at` без вывода из `id`** — требовала бы отдельного индекса или
  повторного похода в БД при `markAsRead`, чтобы узнать партицию по `id`; вывод из `id`
  бесплатен и не требует запроса.

## Последствия

**Плюсы:**

- Удаление старых данных — `DROP TABLE` партиции, O(1) операция без сканирования и без
  VACUUM-долга (см. ADR-0005).
- `markAsRead`/дедуп-поиск с известным `created_at` сканируют одну партицию, а не всю таблицу.
- Локальность вставок в первичном индексе, как у автоинкремента, без единой точки координации.

**Минусы:**

- 4 индекса на вставку (`unread`, `dedup`, `ratelimit`, `undelivered`) — цена записи выше, чем
  у минимальной схемы. Осознанный компромисс: каждый индекс закрывает конкретное требование
  (R1, R6, R5, R9) и подтверждается `EXPLAIN` в `test/integration/schema.spec.ts` и
  `docs/performance.md`.
- Партиционирование требует дисциплины: если `ensure_notifications_partition` не вызывается
  вовремя, строки уходят в `notifications_default` без pruning — закрыто автосозданием
  партиций наперёд (`PartitionMaintenanceService`) и WARN-логом на использование
  default-партиции.
- Клиент, генерирующий не-UUIDv7 значение и передающий его как `id`, сломает partition pruning
  молча — поэтому `uuidV7ToDate`/`assertUuidV7` обязаны бросать ошибку на не-v7 UUID.

## Триггер пересмотра

Пересмотреть гранулярность партиций (например, на недельные) при устойчивом росте нагрузки
на порядок выше расчётных 500k/сутки — сигнал: партиция месяца растёт настолько, что `EXPLAIN`
на ней перестаёт укладываться в целевые p95/p99 из `docs/performance.md`.
