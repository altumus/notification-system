# ADR-0005: Retention через DROP PARTITION, выключен по умолчанию

**Язык / Language:** Русский · [English](./en/0005-retention.md)

← [Все ADR](./README.md)

## Контекст

При 500k уведомлений/сутки (≈250 МБ/сутки, ≈90 ГБ/год — раздел 3.6 плана) хранилище не может
расти бесконечно без операционных затрат. Одновременно удаление данных — необратимая операция:
включать его по умолчанию при первом деплое рискованно, если оператор не успел настроить бэкапы
или неверно понял единицы измерения `RETENTION_MONTHS`.

## Решение

- Партиции создаются помесячно (ADR-0002); `RetentionService` раз в сутки удаляет партиции
  старше `RETENTION_MONTHS` через `DROP TABLE IF EXISTS`, но **только если**
  `RETENTION_ENABLED=true`. По умолчанию `RETENTION_ENABLED=false`, и при старте приложения
  в логах явно пишется, что удаление отключено — оператор не должен догадываться об этом
  по отсутствию поведения.
- Удаляются только партиции, чьё имя прошло строгую проверку регулярным выражением
  `^notifications_\d{4}_\d{2}$`. Имя партиции нельзя параметризовать в DDL (`DROP TABLE $1`
  синтаксически невозможно), поэтому единственная защита от использования непроверенного имени —
  этот allow-list на уровне кода, применяемый непосредственно перед подстановкой строки в SQL.
- Защита от параллельного запуска на нескольких инстансах — `pg_try_advisory_xact_lock` на
  фиксированном ключе внутри транзакции: не получилось получить лок — тихий выход без ошибки.
  Транзакционная версия лока выбрана намеренно (а не сессионная) — она не требует «прикалывать»
  одно физическое соединение пула к паре lock/unlock и снимается автоматически при
  `COMMIT`/`ROLLBACK`, что безопасно при работе через пул соединений.

## Почему `DROP TABLE`, а не `DELETE`

- `DELETE FROM notifications WHERE created_at < ...` по миллионам строк держит блокировки и
  оставляет «мёртвые» версии строк, требующие `VACUUM`, который сам по себе — операция,
  создающая нагрузку на диск и CPU и не гарантирующая мгновенного возврата места ОС.
- `DROP TABLE` партиции — операция уровня каталога (метаданные), не зависящая от количества
  строк в партиции: она выполняется за миллисекунды и сразу освобождает место на диске.
- Побочный эффект в нашу пользу: партиционирование, изначально введённое ради 500k/сутки
  (ADR-0002), делает retention практически бесплатным — эта ADR лишь включает уже
  подготовленную возможность.

## Альтернативы

- **Retention включён по умолчанию** — отклонено: удаление данных не должно быть побочным
  эффектом настроек по умолчанию; оператор обязан осознанно включить его, ознакомившись
  с `RETENTION_MONTHS` и убедившись в наличии бэкапов (`deploy/backup.sh`, коммит 21).
- **`DELETE` с батчами по 10 000 строк** — рассматривался для гибкости (можно удалять «часть
  месяца»), но не даёт преимуществ при полностью устаревших партициях и заметно дороже по
  ресурсам. Оставлен как техника для других операций с большими объёмами (см. `markAllAsRead`
  в коммите 08), но не для retention.
- **Отдельный обслуживающий скрипт вне приложения (cron на хосте)** — отклонено: логика привязана
  к advisory-локу и конфигурации приложения; держать её в одном месте с
  `PartitionMaintenanceService` проще для чтения и тестирования (`@nestjs/schedule` уже
  используется для создания партиций).

## Последствия

**Плюсы:**

- Удаление данных дёшево и предсказуемо по времени независимо от объёма партиции.
- Явный лог-сигнал о текущем режиме retention исключает ситуацию «удаление включено, а никто
  не знает».
- Единая точка валидации имени партиции — компрометация конфигурации (например, инъекция через
  `RETENTION_MONTHS`) не может привести к `DROP TABLE` произвольного объекта, потому что имя
  партиции всегда вычисляется и сверяется с regexp на стороне приложения, а не берётся из
  непроверенного ввода.

**Минусы:**

- Гранулярность удаления — месяц; нельзя удалить «часть» партиции без ручного вмешательства.
  Это осознанный компромисс: более тонкая гранулярность потребовала бы `DELETE` со всеми его
  минусами, описанными выше.
- Retention не восстанавливает данные — единственная защита от ошибочного включения раньше
  времени — регулярные бэкапы (`pg_dump`, коммит 21) и требование проверенного restore.

## Триггер пересмотра

Если появится требование хранить часть данных дольше остальных (например, по типу уведомления
или по пользователю) — потребуется более тонкая гранулярность, чем удаление целой месячной
партиции; тогда стоит пересмотреть схему партиционирования (например, композитное
партиционирование по типу и дате) или ввести отдельный архивный сторидж вместо `DROP TABLE`.
