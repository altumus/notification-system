# ADR-0001: Kysely + SQL-миграции вместо ORM

**Язык / Language:** Русский · [English](./en/0001-kysely-vs-orm.md)

← [Все ADR](./README.md)

## Контекст

Таблица `notifications` партиционирована по `created_at`, использует составной PK `(id, created_at)`,
партиальные индексы, `pg_advisory_xact_lock` и тонкий контроль над планами запросов (`EXPLAIN`).
Нужен типизированный доступ к SQL без потери контроля над DDL.

## Решение

Использовать `pg.Pool` + **Kysely** как типизированный query-builder и **node-pg-migrate**
с миграциями в чистом `.sql`.

## Альтернативы

| Вариант                | Почему отвергнут                                                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Prisma                 | Diff/миграции плохо дружат с declarative partitioning и частичными индексами; теряется контроль над advisory locks |
| TypeORM                | Схема «из декораторов» расходится с реальным DDL партиций; сложные raw-запросы всё равно уходят в обход ORM        |
| Чистый `pg` без Kysely | Работает, но нет compile-time проверки имён колонок и результата `RETURNING`                                       |

## Последствия

- Плюсы: ревьюер видит настоящий SQL; типы не врут про nullable/`bytea`/`timestamptz`; партиции и индексы описываются явно.
- Минусы: больше кода, чем у «магического» ORM; типы схемы нужно поддерживать руками (или через `kysely-codegen` позже).

## Триггер пересмотра

Если появится официальная первоклассная поддержка RANGE-партиций и partial indexes в выбранном ORM
без обходных путей — пересмотреть. До тех пор Kysely остаётся источником типизации, SQL — источником истины.
