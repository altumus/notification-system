# ADR-0006: Idempotency-Key отдельно от бизнес-дедупа

**Язык / Language:** Русский · [English](./en/0006-idempotency-vs-dedup.md)

← [Все ADR](./README.md)

## Контекст

Продюсер уведомлений (очередь at-least-once, таймаут HTTP) может повторить
`POST /notifications` с тем же смыслом. Параллельно действует R6: дубли по содержимому
за 5 минут схлопываются. Нужно не смешивать эти механизмы.

## Решение

Два независимых слоя:

| Слой            | Ключ                              | Окно    | Эффект                                   |
| --------------- | --------------------------------- | ------- | ---------------------------------------- |
| Idempotency-Key | заголовок + sha256(тело)          | 24 часа | тот же HTTP-ответ, без повторного create |
| Дедуп (R6)      | `dedup_hash` по user/type/payload | 5 минут | `occurrences++`, статус `deduplicated`   |

Таблица `idempotency_keys` хранит сохранённый ответ. Параллельный повтор
(ключ занят, ответа ещё нет) → `409` + `Retry-After: 1` вместо блокирующего ожидания.

## Альтернативы

| Вариант                        | Почему отвергнут                                                                 |
| ------------------------------ | -------------------------------------------------------------------------------- |
| Только дедуп R6                | Разный payload/порядок полей при ретрае создаст вторую сущность; нет replay HTTP |
| Блокировка `SELECT FOR UPDATE` | Долго держит соединение при медленном create; хуже 409 + короткий ретрай         |
| Идемпотентность = дедуп-хеш    | Смешивает транспорт и бизнес-правило; ломает осознанные «похожие» события        |

## Последствия

- Плюсы: ретрай безопасен; дедуп остаётся продуктовым правилом; ADR объясняет ревьюеру разницу.
- Минусы: при краше после claim клиент получает 409 до TTL/очистки pending (осознанный компромисс).

## Триггер пересмотра

Если появятся длинные create (>1s) и частые параллельные ретраи — рассмотреть
короткий wait/notify вместо немедленного 409.
