# ADR-0008: Транспортный лимит частоты на IP поверх бизнес-лимита

**Язык / Language:** Русский · [English](./en/0008-http-rate-limit.md)

← [Все ADR](./README.md)

## Контекст

R5 закрыт бизнес-лимитом: не больше 10 уведомлений в минуту на пару `(user_id, type)`
([ADR-0004](./0004-rate-limit-in-postgres.md)). Но этот лимит считается **в PostgreSQL**, внутри
транзакции с advisory-локом. То есть каждый отклонённый запрос всё равно стоит парсинга JSON,
валидации DTO, проверки JWT, соединения из пула и запроса к БД. Флудер получает 429, а сервер
платит за это ресурсами.

Отдельно стоит `POST /auth/dev-token`: маршрут анонимный (`@Public`) и единственный в API,
который жжёт CPU на подписи JWT вообще без участия БД.

## Решение

Добавлен второй, транспортный уровень: `@nestjs/throttler` через `HttpThrottlerGuard`,
зарегистрированный как `APP_GUARD` в `RateLimitModule`.

- Ключ — **клиентский IP** (`req.ips[0]` за `trust proxy`, иначе `req.ip`), а не `userId`:
  до аутентификации `userId` неизвестен, а защищать нужно именно анонимный поток.
- `RateLimitModule` импортируется в `AppModule` **раньше** `AuthModule` — Nest вызывает
  `APP_GUARD` в порядке регистрации, поэтому лимит отсекает флуд до проверки подписи JWT.
- Ведро — пара `(IP, маршрут)` (поведение библиотеки по умолчанию): тяжёлый `POST` не делит
  бюджет с дешёвым `GET`.
- Значения: `HTTP_RATE_LIMIT=300` за `HTTP_RATE_WINDOW_MS=60000`. Для сравнения, демо-страница
  в самом «болтливом» сценарии делает ~20 запросов, а честный клиент упирается в бизнес-лимит
  (10/мин) задолго до транспортного.
- `POST /auth/dev-token` — свой `@Throttle` на 20/мин. Значение намеренно **константа в коде**,
  а не env: это нижняя граница безопасности, а не настройка эксплуатации.
- `/health/live` и `/health/ready` помечены `@SkipThrottle`: пробы docker HEALTHCHECK и Railway
  приходят с одного адреса, и лимит на них уронил бы деплой, а не атакующего.
- Ответ — `problem+json` с кодом `too-many-requests` и заголовками `RateLimit-*` / `Retry-After`.
  Отдельный `type` важен: клиент должен различать «слишком много уведомлений этого типа»
  (`rate-limit-exceeded`, повтор бессмыслен до конца окна) и «слишком много запросов вообще».

## Альтернативы

| Вариант                                 | Почему отвергнут                                                                                                        |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Ограничиться бизнес-лимитом в БД        | Каждый мусорный запрос доходит до Postgres; анонимный `/auth/dev-token` не покрыт вообще                                |
| Лимит на nginx / edge                   | Стенд на Railway без своего reverse-proxy; правило жило бы вне репозитория и не проверялось бы тестами                  |
| Ключ по `userId` вместо IP              | Требует сначала проверить JWT — то есть оплатить именно ту работу, от которой защищаемся                                |
| Общее ведро на IP без разбивки по путям | Пачка дешёвых `GET` выедала бы бюджет на `POST`; при этом маршрутный `@Throttle` конфликтовал бы с общим счётчиком      |
| Сразу `ThrottlerStorageRedis`           | Второй инфраструктурный сервис ради лимита, который на одном инстансе точен и без него (`REDIS_URL` уже зарезервирован) |

## Последствия

- Плюсы: флуд отсекается до БД и до подписи JWT; анонимные маршруты закрыты; контракт ошибок
  не размывается — 429 остаётся `problem+json` с машиночитаемым кодом.
- Минусы:
  - Счётчики живут в памяти процесса. При N репликах эффективный лимит — N × `HTTP_RATE_LIMIT`
    (клиент попадает на разные инстансы). Для защиты от флуда этого достаточно, для точной
    квоты — нет.
  - Клиенты за общим NAT делят ведро. При 300/мин на эндпоинт это заметно только для
    заведомо автоматизированного трафика.
  - Нагрузочные профили k6 идут с одного IP и упираются в лимит, поэтому прогоны требуют
    `HTTP_RATE_LIMIT_ENABLED=false` на стенде (см. [performance.md](../performance.md)).

## Триггер пересмотра

Переход на несколько реплик API. Тогда счётчик уезжает в `ThrottlerStorageRedis` по
`REDIS_URL` — тем же движением, что и Socket.IO-адаптер, потому что обе задачи упираются в
одно: общее состояние между инстансами.
