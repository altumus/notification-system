# ADR-0002: Monthly partitioning + UUIDv7 as primary key

**Язык / Language:** [Русский](../0002-partitioning-and-uuidv7.md) · English

← [All ADRs](../README.en.md)

## Context

The system must sustain ~500,000 notifications/day without degrading. At ~250 B/row and
4 indexes ≈ 500 B → ~250 MB/day, ~90 GB/year. An unpartitioned table with hundreds of millions
of rows degrades on several axes at once:

- indexes grow without a cheap way to shrink storage (`DELETE` does not free disk without
  `VACUUM FULL`, which locks the table);
- retention (“drop data older than N months”) becomes a mass `DELETE` with VACUUM debt and
  long-held row locks;
- with `UUIDv4` as PK, inserts scatter across the B-tree and hurt page locality more than a
  monotonic key would.

## Decision

1. **Range partitioning on `created_at`** (`PARTITION BY RANGE`), monthly partitions plus a
   `DEFAULT` partition as a safety net for unexpected dates.
2. **`id` is UUIDv7**, generated by the app (`uuid@11`, `v7({ msecs })`): time-ordered for
   insert locality like an autoincrement, globally unique without cross-instance coordination.
3. **Composite PK `(id, created_at)`**: partitioned tables require the partition key in every
   unique/primary index.
4. **`created_at` is derived from `id`**: the top 48 bits of UUIDv7 are Unix ms. The public API
   stays “by `id`” (`PATCH /notifications/:id/read`), while `created_at` for `WHERE` is computed
   from `id` — enabling **partition pruning** without an extra lookup.
5. **Invariant:** `created_at` is written as `new Date(msecs)` from the same `msecs` used for
   `id` (millisecond precision). `msecs` comes from the DB `clock_timestamp()`, not the Node
   process clock, to avoid skew across app instances.

## Alternatives

- **`UUIDv4` as PK** — random inserts break page locality; rejected.
- **`BIGSERIAL`** — equally local, but needs a DB sequence (coordination point) and leaks
  volume/order into the external API.
- **Weekly partitions** — monthly is a better balance at current volume; revisit if load grows.
- **Independent `created_at` column** — would need an extra index or round-trip to find the
  partition on `markAsRead`.

## Consequences

**Pros:** old data drops via `DROP TABLE` of a partition (O(1), see ADR-0005); `markAsRead`/dedup
scans one partition; insert locality without a single coordination point.

**Cons:** 4 indexes per insert (unread, dedup, ratelimit, undelivered) — deliberate write cost;
partition maintenance discipline required (`PartitionMaintenanceService`); non-v7 ids must be
rejected by validation.

## Revisit trigger

Switch to weekly partitions if monthly partitions grow so large that `EXPLAIN` no longer meets
target p95/p99 under sustained load far above 500k/day.
