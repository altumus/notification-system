# Производительность и нагрузочное тестирование

**Язык / Language:** Русский · [English](./en/performance.md)

← [Индекс документации](./README.md)

Требование R4 — выдерживать 500 000 уведомлений/сутки. Ниже расчёт ёмкости, целевые
показатели и профили k6, которыми это проверяется.

## Что означает 500k/сутки

| Метрика                      | Значение                            |
| ---------------------------- | ----------------------------------- |
| Средний поток записи         | 500 000 / 86 400 ≈ **5.8 rps**      |
| Пик ×10 (неравномерный день) | ≈ **60 rps**                        |
| Строка + 4 индекса           | ≈ 250 Б + 250 Б ≈ **500 Б**         |
| Прирост данных               | ≈ **250 МБ/сутки**, ≈ **90 ГБ/год** |
| Строк в месячной партиции    | ≈ **15 млн**                        |

Средняя нагрузка невысокая — основной риск не в RPS, а в накоплении объёма: без
партиционирования индексы на сотнях миллионов строк деградируют, а `DELETE` для retention
создаёт VACUUM-долг. Как это решено — [ADR-0002](./adr/0002-partitioning-and-uuidv7.md) и
[ADR-0005](./adr/0005-retention.md).

## Целевые показатели

| Операция                    | Цель p95 | Цель p99 | Почему так                                                        |
| --------------------------- | -------- | -------- | ----------------------------------------------------------------- |
| `POST /notifications`       | < 200 мс | < 500 мс | транзакция с advisory-lock и до 4 запросов внутри                 |
| `GET /notifications/unread` | < 100 мс | < 250 мс | keyset по частичному индексу, без транзакции                      |
| `GET .../unread/count`      | < 100 мс | < 250 мс | подсчёт с ограничением `cap + 1`                                  |
| Доставка по WebSocket       | < 200 мс | —        | push идёт после COMMIT, замеряется в `test/e2e/realtime-delivery` |

Планы запросов дополнительно фиксируются через `EXPLAIN` в
`test/integration/schema.spec.ts` и `test/integration/notifications-read.spec.ts` — это
защита от «тихой» потери индекса или partition pruning при рефакторинге.

## Профили k6

Сценарии лежат в [`load/`](../load). Нужен [k6](https://k6.io/docs/get-started/installation/)
и поднятый стенд (`make up`).

| Файл                           | Что проверяет                                              |
| ------------------------------ | ---------------------------------------------------------- |
| `load/create-notifications.js` | запись: много получателей, разные типы, уникальные payload |
| `load/read-unread.js`          | чтение: список непрочитанных и счётчик бейджа              |
| `load/hot-pair.js`             | худший случай: вся нагрузка в одну пару `(userId, type)`   |

Профиль задаётся через `LOAD_PROFILE`:

| Профиль    | Запись  | Чтение   | Назначение                               |
| ---------- | ------- | -------- | ---------------------------------------- |
| `baseline` | 6 rps   | 50 rps   | средняя суточная нагрузка при 500k/сутки |
| `peak`     | 60 rps  | 300 rps  | пик ×10                                  |
| `stress`   | 300 rps | 1000 rps | ×50: ищем начало деградации              |
| `ci`       | 20 rps  | 50 rps   | короткий прогон в пайплайне              |

```bash
make up                                    # поднять стенд
pnpm load                                  # запись, baseline
make load-peak                             # запись, пик ×10
pnpm load:read                             # чтение
pnpm load:hot-pair                         # горячая пара
k6 run -e LOAD_PROFILE=stress load/create-notifications.js
```

Против внешнего стенда:

```bash
k6 run -e BASE_URL=https://your-app.up.railway.app load/create-notifications.js
```

Требуется `AUTH_DEV_TOKENS_ENABLED=true` — сценарии сами получают service-токен через
`POST /auth/dev-token`.

## Как читать результаты

- **429 — это не ошибка.** Профили помечают `429` ожидаемым статусом: сработавший rate limit
  подтверждает R5. В `http_req_failed` попадают только настоящие сбои.
- **`notifications_created` / `notifications_deduplicated` / `notifications_rate_limited`** —
  кастомные счётчики: показывают, во что превратилась нагрузка.
- **`hot-pair` намеренно деградирует по латентности.** Создание берёт
  `pg_advisory_xact_lock` на `(userId, type)`, поэтому запросы к одной паре сериализуются.
  Смысл сценария — найти границу, за которой стоит выносить счётчик в Redis
  ([ADR-0004](./adr/0004-rate-limit-in-postgres.md)), а не показать хорошие числа.
- **Порог `thresholds` проваливает прогон** — k6 вернёт ненулевой код выхода, поэтому профиль
  `ci` в пайплайне работает как регрессионный тест производительности, а не как отчёт.

## Ограничения текущей конфигурации

- **Один инстанс API.** `PresenceRegistry` держит сокеты в памяти процесса, а доменные
  события идут через in-process `EventEmitter2`. При нескольких репликах live-push работает
  внутри инстанса, а межинстансную доставку добирает `UndeliveredSweeper` (задержка —
  `SWEEPER_MIN_AGE_MS`, по умолчанию 30 с). Для 500k/сутки одного инстанса достаточно; для
  отказоустойчивости нужен общий adapter (`REDIS_URL` зарезервирован под это).
- **Rate limit считается в Postgres** запросом по индексу, а не в отдельном хранилище.
  Компромисс и триггер пересмотра — [ADR-0004](./adr/0004-rate-limit-in-postgres.md).
- **Числа зависят от стенда.** Локальный `docker compose` и Railway дают разные результаты:
  сравнивать имеет смысл прогоны на одной конфигурации, а не абсолютные значения между средами.
